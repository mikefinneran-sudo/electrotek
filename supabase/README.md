# supabase/ — demo database runner, and the tree a client deploy applies

Aggregated migration set + seed for the **bananaforce-demo** Supabase project
(BananaFORCE org, region `us-east-1`). This is the single-database demo that
mounts every module at once in `apps/_template` — and it is also the tree a
real client deploy applies. `apps/<slug>/MIGRATIONS.md`, generated by
`scripts/goat/migration-order.ts` (`renderMigrationDoc`), tells a deployer to
run every file in this directory, in filename order, against the client's own
Supabase project. That list is **not** filtered to the modules the client
enables — `apps/waltersignal/MIGRATIONS.md` lists every file in this
directory even though `apps/waltersignal/client.config.ts` enables 10 of the
20 modules that own migrations. Whatever ships here ships to every client.

## Full schema, every client — this is deliberate (WAL-580)

`resolveMigrationPlan()` in `scripts/goat/migration-order.ts` builds its
`central` list from every `.sql` file in this directory, with no module
argument: `sqlFilesSorted(join(repoRoot, "supabase", "migrations"))`. The
enabled-module list passed into `resolveMigrationPlan` only produces
`byModule`, which `renderMigrationDoc` renders into `apps/<slug>/MIGRATIONS.md`
as a reference section — it does not narrow `central`, which is the actual
apply checklist. A client enabling 10 of the catalog's 21 modules still
receives all 46 migrations: tables, RLS policies, triggers, and functions for
every module, enabled or not. This was raised as a possible defect and closed
by Mike on 2026-08-12 as intended behavior, not a gap to fix.

**Why filtering `central` by enabled modules was rejected.** The aggregate
order in this directory is not a list of independent per-module blocks; it is
one sequence resolved for cross-module FK dependency, per "Migration order"
below. `0000_admin_foundation` is split out and runs first, and
`0016_admin_policies` is split out and runs last, specifically because that
dependency graph does not decompose into contiguous per-module slices — a
client enabling a subset of modules cannot simply skip the files for the
modules it excluded, because later files depend on tables and functions those
files define, and non-enabled modules' files are sometimes load-bearing for
enabled ones (`admin`'s two-part split is the clearest case, but not
necessarily the only one). Building a real per-client subset would mean
resolving a distinct FK-consistent apply order per module combination, then
keeping each client's database on its own migration path — which breaks the
one property this aggregate exists to guarantee: a single ordered sequence
that `pnpm check-migrations` can hash and diff against the per-module trees
(see "Drift between the two trees is checked," below) and that
`scripts/assert-migration-head.sh` can assert against in CI. Per-client
divergence turns that one check into one check per client, with no aggregate
left to check it against.

**What this means in practice: `client.config.ts` gates the app, not the
database.** A client's Supabase project ends up with the full schema for all
21 modules regardless of which ones `client.config.ts` enables. `supabase/config.toml`
exposes the `public` schema over the Data API (`schemas = ["public", "graphql_public"]`),
so every module's tables — enabled or not — are reachable at
`/rest/v1/<relation>` by anyone holding an anon or authenticated key, whether
or not the client's app routes to that module. `client.config.ts` controls
what the app *renders*; it has no bearing on what the database *exposes*. RLS
is therefore the only gate on that surface, and it has to hold for the whole
catalog in every client's database — not only the modules that client turned
on. WAL-586 tracks the suite that asserts deny-by-default across the entire
catalog for exactly this reason: because every client's database enforces
(or fails to enforce) all 21 modules' policies, "does this database enforce
X" has to be a catalog-wide question, not a per-client one.

That also settles a question this decision could otherwise raise: whether a
client should be able to see modules it hasn't enabled. It can, and that is a
UI concern, not a schema one (WAL-585) — the module catalog is compile-time
TypeScript (`packages/modules/src/index.ts`), so a locked-row directory of
unpurchased modules costs no additional tables and requires no schema
filtering to implement.

> The per-module migrations in `packages/module-*/supabase/migrations/` are
> each module's own source — a migration is authored and reviewed there, next
> to the module's code, before it is copied into this directory. They are
> **not** what a client deploy applies and are not read by `goat`. This
> directory is what a deploy applies, and it is only a copy: nothing keeps it
> current except `pnpm check-migrations` (below), which hashes every file in
> both trees on every push and fails the build on drift it cannot explain via
> `migration-manifest.json`. If you change a module's migration, copy it into
> the next slot here (regenerate, below) and let that check — not habit —
> confirm the two trees still agree. Neither reading of "source of truth"
> licenses letting the other tree rot: a migration that reaches only the
> per-module tree never ships to a client (this happened — WAL-390's
> `resolve_order_item_unit_price`, closed by WAL-568); a migration added only
> here without an owning module is a gap in the other direction, which is
> exactly what `moduleOnly` below exists to catch.

## Migration order (FK dependencies)

Modules are renumbered so base tables exist before anything references them:

1. `0000_admin_foundation` — `public.staff` + `public.is_staff()`. **Runs first**
   because nearly every other module's RLS policies call `is_staff()`.
2. `0001_catalog` … `0004_billing` — create the shared base tables
   (`products`/`locations`/`customers`, `accounts`/`contacts`, `inspections`,
   `invoices`) that downstream modules reference.
3. `0005`–`0015` — the remaining modules (dependents after their bases).
4. `0016_admin_policies` — admin's staff_* RLS policies on catalog/ordering
   tables. **Runs last** because it attaches to those tables.

`admin` is the only module split in two: its foundation must precede everyone,
its commerce policies must follow catalog/ordering. Everything else is a 1:1
copy of the module's `0001_*.sql`.

## Regenerate after a module migration changes

```bash
order=(catalog crm quote-engine billing lead-capture ordering contract-esign \
  visit-checkflow client-portal scheduling ticketing asset-controls \
  communications accounting reporting admin)
# (admin is split by hand into 0000_admin_foundation + 0016_admin_policies)
```

See the loop in the session that created this dir, or rebuild by copying each
`packages/module-<name>/supabase/migrations/0001_*.sql` to the numbered slot.

## Drift between the two trees is checked

```bash
pnpm check-migrations           # fails the build on drift
pnpm check-migrations -- --report   # print the full reconciliation
```

Regeneration is manual, so for a long time nothing noticed when it did not
happen — which is how WAL-390's server-side price resolution came to exist in
`packages/module-ordering/` and in no aggregate file. `scripts/check-migrations.mjs`
now reconciles the two trees on every push.

Most aggregate files are byte-identical copies of a module migration and are
matched by content hash, so **adding a module migration and copying it to the
next slot needs no bookkeeping at all**. Only three exceptional kinds are
declared in `migration-manifest.json`:

| Kind | Meaning | What fails the build |
|---|---|---|
| `derived` | Built from named module sources — a split, a merge, a renumbered header | Editing a source without regenerating the aggregate file |
| `aggregateOnly` | Cross-cutting migration no module owns | Adding one without a reason and a tracking issue |
| `moduleOnly` | A module migration that never reached the aggregate — a known gap | Adding a new module migration that is not copied across |

**Both lists are currently empty**, and should stay that way. WAL-568 closed the
gaps WAL-562 baselined: the five module migrations that had never been copied
across now occupy slots `0041`–`0045`, and the three cross-cutting migrations no
module owned were moved into owning modules (`0025_audit_log` to admin, and
`0035`/`0036` split across the modules that own the buckets and functions).

Do not add to either list to make a red build green — copy the migration into
the next aggregate slot instead. A `moduleOnly` entry means a client deploy
does **not** get that migration, because a deploy applies this aggregate, not
the per-module trees — that is the gap WAL-390 fell into. An `aggregateOnly`
entry means the opposite risk: every client gets that migration whether or
not any module it "belongs to" is enabled, because the aggregate is applied
in full regardless of a client's module selection, so it needs a reason and a
tracking issue to justify existing with no module accountable for it. Both
are risks wearing a reason string; declaring one in the manifest does not
close it, only names it.

## Notes on specific migrations

A few files in this tree carry constraints the filename alone does not show:

- **`0041_order_price_resolution.sql`** is WAL-390's server-side price
  resolution (`resolve_order_item_unit_price`) — the fix that makes
  `unit_price` validate against the catalog instead of trusting client input.
  It, along with `0042`–`0045`, was backfilled by WAL-568 after WAL-562 found
  these five module migrations had reached their owning module but never this
  aggregate — meaning every client deploy up to that point applied an
  aggregate missing them, not only the demo.
- **`0037_quote_lifecycle_enum.sql`** and **`0038_quote_lifecycle.sql`** are a
  deliberate two-file pair and must not be merged. `0037` adds the `viewed`
  and `expired` labels to the `inspection_status` enum; Postgres will not let
  an executed statement *use* a new enum label until the transaction that
  added it has committed. Keeping the label change in its own committed
  migration means a later edit to `0038` — a check constraint, an index
  predicate, a backfill `update ... set status = 'expired'` — cannot fail on
  deploy against a live database. See the header comment in `0037` before
  touching either file.
- **Per-module `*_pin_function_search_path.sql` files** land at whatever slot
  number is next free in that module, not at a fixed number — `ticketing`'s is
  `0004` because `0003` was already `0003_ticketing_email_source.sql`;
  `quote-engine`'s is `0007` because `0004`–`0006` were already the
  quote-lifecycle migrations. `0036_pin_function_search_path.sql` here is a
  `derived` entry in `migration-manifest.json`: it was originally one
  aggregate-only file with all 14 `alter function ... set search_path` pins,
  then split so each owning module carries its own (12 module files, 13 of
  the 14 statements — `enforce_order_item_total` stays in `ordering`'s
  `0003`, which already pins it, deliberately). Editing a source file without
  updating `0036` and its recorded hash fails `pnpm check-migrations`.

## Applying the set from empty is checked

The `database` job in `.github/workflows/ci.yml` runs `supabase start` on the
GitHub runner and applies every migration to an empty database on each push,
then `scripts/assert-migration-head.sh` asserts the applied versions match the
files on disk exactly. Nothing runs locally and no cloud project is involved.

Ordering constraints are now enforced by a database rather than by a numbering
convention. That matters most for the cases a schema dump cannot show — for
instance, Postgres will not let an executed statement use a new enum label until
the transaction that added the label has committed, so a migration pair split
for that reason stays split, and merging it fails here.

## Apply / reset

```bash
supabase link --project-ref <ref> --password <db-password>
supabase db reset --linked   # replays all migrations + seed.sql (DESTRUCTIVE)
```

## seed.sql

Demo data for a fictional janitorial + fireworks-retail business ("Sparkle
City"). Populates every module. Notes:

- Pipeline stages (`crm`) and `task_library` (`quote-engine`) are seeded by their
  migrations — seed.sql references those, it does not re-insert them.
- `customers` rows are auto-created by catalog's `on_auth_user_created` trigger
  when the demo `auth.users` rows insert; seed.sql upserts to set tier/approved.
- Demo `auth.users` use placeholder password hashes (these users never sign in).
